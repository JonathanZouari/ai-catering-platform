תאריך עדכון: 2026-11-09 · ריפו מקור: JonathanZouari/ai-catering-platform · Fork: iditwein/ai-catering-platform

1. מהו הפרויקט

אפליקציית הזמנות וניהול לעסק קייטרינג יחיד (עברית, RTL, מובייל תחילה). הלקוח בונה הזמנה, הבק-אנד מחשב מחירים וכמויות, ועוזר AI רק מציע שינויים שמתבצעים אחרי אישור מפורש של הלקוח. הבעלים מאשר או דוחה כל הצעת מחיר.

שכבהטכנולוגיה
BackendPython 3.12+, FastAPI, Pydantic (SQLAlchemy בשלב 2)
FrontendHTML, CSS ו-JavaScript רגיל, מוגש ע"י FastAPI
DataSupabase (Postgres, Storage, Auth)
HostingRailway (Dockerfile)
איכותpytest, Ruff, GitHub Actions

2. מה עשינו בסשן הזה

  1. שיבוט הריפו לתיקייה AI CATERING_2/repo עם כל הענפים כענפים מקומיים: main, dev, feat/supabase-foundation, feat/ui-redesign-catering. (ניסיון ראשון כ-mirror נמחק.)
  2. משיכת שינויים מכל הענפים (fetch --all --prune ו-pull --ff-only לכל ענף). הכול היה מעודכן.
  3. סנכרון ה-Fork של איידית מול הריפו של יונתן: main סונכרן עם gh repo sync; שלושת הענפים האחרים לא היו ב-fork ולכן נדחפו מהשיבוט המקומי. בענפים נוספים ב-fork (feat/backend-supabase, feat/sqlite-db, feat/supabase-cloud) לא נגענו.
  4. יצירת CLAUDE.md עם פקודות פיתוח, ארכיטקטורה והערות עבודה.
  5. הוספת סעיף "After completing any change" ל-CLAUDE.md: אחרי כל שינוי מריצים ruff (כולל כללי אבטחה S), בדיקת פורמט, pytest, ובודקים שלא נכנסו סודות ל-staging.
  6. הרצת הבדיקות: ruff check עבר, 12 קבצים מפורמטים, 2 בדיקות pytest עברו (אזהרת deprecation אחת של httpx/starlette). backend/.venv מוחרג ב-.gitignore.

5. ארכיטקטורה בקצרה

  • שירות FastAPI אחד מגיש API ופרונטאנד סטטי (frontend/ מוצמד ל-/ אחרון, כך שנתיבי API מנצחים).
  • שכבות מתוכננות: api → services → repositories → models + schemas ו-agents. שכבה תחתונה לא מייבאת עליונה.
  • הבק-אנד סמכותי למחירים, כמויות ומצב הזמנה. סוכן ה-AI קורא רק לפונקציות שירות מוגדרות, וכל שינוי עובר הצעה → אישור → ביצוע.
  • זרימת לקוח ב-4 שלבים: event → menu → summary → status, על mock backend בשלב זה.
  • אלרגן null = לא ידוע, ולעולם לא מוצג כבטוח.
